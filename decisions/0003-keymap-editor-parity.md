**Date:** 2026-11-25

Follow-ups in the same session: "make sure proper keymap editing is covered by tests so that it can compile. you can use my piantor bt and adv360 repos to check" / "dont use the exact layout in tests of course, but a sample kinds" / "when clicked on a key and something is changed, add Revert button to the popup" / "Can you have the picker basically show a standard qwerty keyboard to pick with modifiers working like modifiers and effective key shown at the top. Replaces the "Editing behavior/macro definitions" non-goal (overview.md) and the first six roadmap items.

## What landed

### Keymap model and writer (internal/keymap)

- `Behavior` gains `id` (label as read), `label` (current; renaming changes it), `props` (every property except compatible, #binding-cells, #sensor-binding-cells, bindings, label, display-name). Kind `sticky-key` added.
- `Prop {name, type, value}`: `bool` (no value), `cells` (one `<...>` group, cells space-joined), `string` (unquoted), `raw` (devicetree text as written). `props.go` diffs props by name: changed values replaced in place, removed ones deleted, new ones appended before the closing brace.
- `behaviors.go`: behaviors are matched by `id`; label rename edits the label at the node start; compatible, #binding-cells, display-name (or legacy `label`) and bindings are set as needed. Bindings keep the file's style: inline `<a>, <b>`, leading-comma multi-line or trailing-comma multi-line; a macro's `&macro_param_*` steps share the group of the binding they feed. New behaviors go into an existing `macros` (macros) or `behaviors` node under `/`, else a new `behaviors` node before the keymap node. Labels are validated (identifier, unique, not used by another node).
- `Override {id, ref, props}`: top-level `&ref { ... };` nodes without children (e.g. `&mt { tapping-term-ms = <..>; };`). Edited with the same prop diff; new ones are inserted before the first `/ {` node; at most one per ref.
- Conditional layers are editable (`id`, `read_only` added): if-layers, then-layer, node name; created in a `conditional_layers` node before the keymap node when missing.
- Layer reordering is supported: existing layer nodes are slots and each slot receives the edited text of the layer now at that position, so comments between layers stay put; new layers may be placed anywhere. Renumbering references is the client's job (below).
- `#define` values are editable: the parser records `DefineSpans` for single-line object-like defines and `Apply` rewrites changed values (`#define NAV 2` after a reorder).
- Multi-line bindings keep the row indentation the file uses (including none).
- `check.go` `Check(model, builtins, external)`: build-breaking problems without a toolchain: unknown behavior references, wrong parameter counts (commands per the catalogue), layer indexes and combo positions out of range, layers with a different binding count, hold-tap/mod-morph binding counts, macro compatible vs #binding-cells and parameter use.
- `Save` returns `problems`: problems in the written file that the file did not have before (so references to behaviors from included files are not reported every time). The UI shows them in a warning toast.
- `behaviors.json` gains the macro control behaviors (`&macro_tap`, `&macro_press`, `&macro_release`, `&macro_pause_for_release`, `&macro_wait_time`, `&macro_tap_time`, `&macro_param_XtoY`) flagged `macro: true`, offered only inside macros.

### Tests

- New fixtures written for the tests (not copies of real configs), modelled on common real-world shapes: `split36.keymap` (one-line layers, comments between behavior properties, display names, capitalized node names, layer `#define`s, mod-morph, tap-dance), `wide.keymap` (irregular rows, legacy `label` properties, a misspelled property, `#include` inside `behaviors`, a behavior from another file, an `&mt` override), `minimal.keymap` (tabs, no containers).
- `assertCompiles` runs after every edit test: no new parser warnings, applying the re-parsed output is the identity, and `Check` finds nothing. When `ZMK_EDITOR_DTC` (a dtc binary) and `ZMK_EDITOR_ZMK` (a zmk checkout; optional `ZMK_EDITOR_ZEPHYR`) are set it also runs `cpp` + `dtc` on the output with stubs for external labels.
- `TestExternalKeymaps` (skipped unless `ZMK_EDITOR_SAMPLES` points at zmk-config checkouts) round-trips every keymap and applies a rename, a property edit, a cross-layer swap and a layer move. Run against the user's Piantor and Adv360 configs: all pass.

### Layouts (internal/layout)

- New source `zmk`: `zmk_layouts.json.gz` (about 10 KB, 80 keyboards) embeds the physical layouts of the shields and boards in ZMK's repository, keyed by directory and keymap name; generated by `go run ./internal/layout/gen /path/to/zmk` (follows `#include`s into `app/dts`; physical layouts, else matrix transforms). Matched by keymap name (also without `_left`/`_right`) and key count.
- New source `matrix`: a `zmk,matrix-transform` in the repository. RC() values are wiring, not position (many boards wire everything as row 0), so keys are placed by where each entry sits in the `map` text (line = row, character column / the most common spacing = x). `Grid()` returns nil for it so it never reformats the keymap.
- Order: custom, JSON, repository physical layout, ZMK built-in, repository matrix transform, generated grid.

### Frontend

- **Behaviors tab** rebuilt: sidebar (defined in this keymap, built-in settings, conditional layers, built-in reference) with a New menu (hold-tap, mod-morph, tap-dance, macro, sticky key, conditional layer, settings of `&mt`/`&lt`/`&sk`/`&sl`/`&caps_word`). Per-kind schemas (`lib/zmk/behaviorSchemas.ts`) drive the form: enums, numbers, switches, modifier flag chips, and hold-trigger key positions picked on the keyboard. Unknown properties are edited as raw devicetree. Rename updates every binding that uses the behavior; delete is blocked while it is used (the places are listed).
- **Macro editor**: steps with drag (and up/down) reordering, control steps as readable rows, wait/tap time inputs, "Use parameter" per binding parameter (inserts `&macro_param_XtoY` and `MACRO_PLACEHOLDER`), compatible/#binding-cells derived from the parameters used, warnings for misused parameters. The catalogue infers a parameterized macro's parameter types from where they are passed.
- **Layer reordering**: drag in the layer list or Move up/down. `lib/zmk/renumber.ts` renumbers layer parameters of every binding (built-ins and custom behaviors whose parameter is a layer, e.g. hold-taps on `&mo`), combo layers, conditional layers and layer `#define`s. Deleting a layer now renumbers the layers after it too; references to the deleted layer are counted in the dialog and left as they are.
- **Keys**: Shift/⌘ click multi-select with a selection bar (set binding, transparent, none, copy, paste, revert); ⌘C/⌘V (one binding pastes onto every selected key, several paste onto the same positions, also across layers); ⌘A selects all; drag a key onto another to swap (⌥ copies); **Swap keys** mode and a "Swap with..." button in the key popover: click the source, switch layers if needed, click the destination. The key popover has **Revert** (back to the binding as loaded) when the key changed, and Copy.
- **Key code field**: the searchable dropdown with autocomplete, then three buttons. (Superseded in the same session: the separate ZMK text button was removed.) Keyboard opens a large dialog with a US ANSI keyboard (plus navigation cluster and media keys, 50 px keys): modifier toggles wrap the key (`LC(LS(A))`), the resulting key is shown at the top, clicking a key applies it and the dialog stays open. ZMK (code icon) opens a popover where the key code is typed in ZMK syntax in any case (`la(ls(n1))`, `&kp LC(A)`, hex), previewed and validated against the key code catalogue before Apply. Capture (record icon) takes the next key pressed. The compact modifier chips stay under the field. Key code params of kind `mod` use the same field without modifier functions. Modifier keys on the picker keyboard act as held modifiers (they wrap the chosen key; clicking the chosen key again leaves the modifiers alone as the key, e.g. `LS(LCTRL)`), and capture records chords: modifiers are collected while held and the first other key finishes (Ctrl+Shift+A -> `LC(LS(A))`); releasing modifiers alone records them. Normal keys are not combinable inside one `&kp` (it sends one key code), so for a plain `&kp` binding in the layer key popover every picker key is toggleable: selecting a second normal key starts a chord, previewed at the top, and "Create macro" adds (or reuses an identical) macro `chord_<keys>` that does `&macro_press` on the modifiers then the keys, `&macro_pause_for_release`, `&macro_release` on the same keys, with display name "LCTRL + Q + W", and binds the key to it. Keycaps of such macros show the keys (⌃+Q+W). Inside other behaviors' parameters (hold-tap tap slots) a macro cannot be a parameter, so there keys still replace each other. (First version showed the keyboard inline under the field; the user found it too small and cramped, so it moved into the dialog.)
- **Export**: current layer or all layers as SVG or PNG (`lib/export/keymapImage.ts`), with the theme's colours resolved to rgb.
- **ZMK binding field** (was "Devicetree"): read-only text of the binding with an Edit button; hovering the label explains it is the devicetree text in the .keymap. Edited text is validated before Apply (`lib/zmk/validate.ts`): known behavior, not a macro-only step, encoder vs key, parameter count (command macros may take one or two cells), key codes against the catalogue (any case, normalized), layers in range, commands from the behavior's list, enums; defines and `MACRO_PLACEHOLDER` pass. Esc cancels the edit without closing the popover.
- **Revert** (`revertKeys` in `lib/zmk/edit.ts`) restores the swap partner too: a changed key whose original binding now sits at another changed position (any layer), which in turn originally held this key's binding, is reverted with it. Macros created in this session (no `id`) that end up unused after a revert are removed.
- Number keys show digits (`N1` -> `1`); `MACRO_PLACEHOLDER` shows as `‹param›`.
- **Keycap symbols**: a key code without a catalogue symbol takes the character from its description (`# [Hash / Pound]` -> `#`, keypad `1`, `ろ (International 1)`), so shifted aliases (`EXCL`, `AT`, `HASH`, `DLLR`, `PRCNT`, `CARET`, `AMPS`, `STAR`, `UNDER`, `PLUS`, ...) show their symbol instead of the name.
- **Picker covers every ZMK key code**: two tabs. *Keyboard* is a full-size board (ANSI main block, navigation cluster, numpad incl. `=`, `(`, `)`, Clear, comma; 48 px keys) plus media keys. *Other keys* lists every remaining key code from the catalogue (aliases merged, one button each, symbol or short description plus the code) grouped as Symbols, Function keys (F13-F24), Editing and system, Media and device, Keypad, International, Launch apps, App controls, Menu and TV, Media sources, Input assist, with a filter. The dialog opens on the tab holding the current key; both tabs have the same fixed height.
- **Recent behaviors** replace the fixed Transparent / None buttons of the binding editor: chips under the behavior picker for the five most recently picked behaviors (picker or chip), newest first, kept in `localStorage` (`lib/recentBehaviors.ts`, starts as Key Press, Transparent, None, Momentary Layer, Mod-Tap). Only behaviors that fit the field are shown (encoder behaviors for encoders, macro steps only in macros).
- **Paste in the key popover**: next to Copy, shown once something is copied and it differs from the key; one copied binding pastes onto this key, several paste back onto their positions on this layer (same as ⌘V). The copy buffer moved from a ref to state so the button appears right after Copy.
- **Modifiers on hold keys**: hold slots (`&mt`, custom hold-taps) and `mod` params (`&sk`) take modifier functions too, since they are sent through `&kp`: `&mt LS(LCTRL) A` holds Shift + Ctrl. (Earlier in the session they were restricted to a single key; that was wrong.)

## Not done, and why

- Editing keymaps whose layers or behaviors are generated by preprocessor macros: edits cannot be written back through macros safely. They keep the notice; such behaviors are not listed.
- A read-only `cpp` preview of those keymaps: needs a C preprocessor and ZMK's headers, which a zmk-config repository does not have.
- Editing behaviors defined in other `.dtsi` files and behaviors that only exist on ZMK feature branches.
- The real `dtc` compile in tests is opt-in through environment variables; building dtc locally was not done in this session.
